# Unit-тесты: vitest и jest

Приоритет у правил репозитория (`CLAUDE.md`). E2E (Playwright, `packages/e2e`) описаны в скилле `qa-automation`.

## vitest + Testing Library (apps/web)

- Команды: `pnpm --filter web test:run`, конфиг `apps/web/vitest.config.ts`, setup `vitest.setup.ts`.
- Запрос по роли и тексту (`screen.getByRole`), `userEvent` вместо `fireEvent`.
- Тестируй поведение для пользователя, не внутреннее состояние и не детали реализации.
- Компоненты с next-intl оборачивай в провайдер сообщений; серверные компоненты и `proxy.ts` проверяй через e2e.
- Сеть мокай на границе (`vi.mock` для модуля запросов или `msw`), не внутри компонента.
- Пример в репозитории: `widgets/auth/auth-form-button/auth-form-button.test.tsx`.

## jest (apps/api)

- `*.spec.ts` рядом с файлом. Сервисы: мок repository через `Test.createTestingModule` и `useValue`.
- Контроллеры и guards: `supertest` с тестовой БД, не dev. Каталога `apps/api/test` и `jest-e2e.json` пока нет (скрипт `test:e2e` указывает на них): при добавлении первого e2e создай их или поправь скрипт.
- Проверяй не только успех: 401 / 403 для чужих данных, 400 для невалидного DTO, 404, конфликт.
- Очереди: тестируй обработчик как обычную функцию, включая повторную доставку одного сообщения (идемпотентность).
- Stripe: вебхуки проверяй с подписью на тестовом секрете, без обращения к сети.

## Что тестировать в первую очередь

Happy path, ошибки валидации, граничные значения, права доступа (чужие данные), повторная и параллельная отправка, поведение при падении сети или API.

## Чего не делать

- Тесты, повторяющие реализацию (мок всего и проверка вызовов).
- `setTimeout` и реальное время: используй fake timers.
- Общий изменяемый state между тестами и зависимость от порядка.
