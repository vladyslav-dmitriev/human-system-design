# Безопасность веб-приложения

Приоритет у правил репозитория (`CLAUDE.md`). Эти проверки делают авторы и агент `security`.

## Авторизация и доступ (OWASP A01)

- **Guard на каждом эндпоинте Nest**; публичные помечай явно и осознанно.
- **IDOR**: ресурс по id всегда запрашивай с условием владельца (`where: { id, userId }`) или проверяй роль. Никогда не доверяй `userId` из тела или query: бери его из токена (`req.user`).
- Проверка прав в сервисе, не только в UI. Скрытая кнопка не защита.
- Mass assignment: `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true })`; в DTO нет полей `role`, `isAdmin`, `userId`, которые клиент не должен задавать.
- Админские и внутренние эндпоинты отделены и закрыты ролью.

## Аутентификация и сессии (A07)

- Пароли: argon2 / bcrypt с солью, никогда в открытом виде и не в логах.
- JWT: короткий срок access-токена, refresh с ротацией и возможностью отзыва, алгоритм зафиксирован, `exp` проверяется.
- Cookies: `httpOnly`, `secure` в проде, `sameSite` (`lax` / `strict`). Токены не в `localStorage`.
- Защита от перебора: rate limiting (`@nestjs/throttler`) на вход, регистрацию, сброс пароля и отправку писем; captcha там, где она есть (`modules/captcha`).
- Сообщения об ошибках входа не раскрывают, существует ли аккаунт.

## Ввод и инъекции (A03)

- Валидируй всё на сервере (`class-validator` в Nest, zod в web); клиентская валидация это удобство, не защита.
- SQL: только Prisma-запросы или `$queryRaw` с параметрами; никакого `$queryRawUnsafe` / конкатенации с пользовательским вводом.
- XSS: React экранирует по умолчанию. `dangerouslySetInnerHTML` только с санитизацией (DOMPurify) и обоснованием. HTML писем (react-email) не собирай из сырого пользовательского ввода.
- Пути и файлы: не строй путь из пользовательского ввода; ключи S3 генерируй сам, проверяй тип и размер, presigned URL с коротким сроком и минимальными правами.
- SSRF и open redirect: URL из ввода проверяй по allowlist хостов; `callbackUrl` и `redirect` только на относительные пути своего приложения.
- Команды ОС и `eval` с пользовательскими данными запрещены.

## CSRF, CORS, заголовки (A05)

- CSRF: cookie с `sameSite`, для cookie-аутентификации мутации защищай токеном или проверкой `Origin`; Server Actions Next проверяют origin, но не отключай эту защиту.
- CORS: конкретные origin из конфига, не `*` вместе с credentials.
- Заголовки: `helmet` в Nest; в Next/nginx: `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `Strict-Transport-Security`, `X-Frame-Options` / `frame-ancestors`.
- Не отдавай стектрейсы и внутренние ошибки клиенту; единый exception filter.

## Данные и секреты (A02, A09)

- Секреты только в env и менеджере секретов; нет в коде, в git, в образах, в `ARG`, в `NEXT_PUBLIC_*`.
- Не логируй токены, cookies, пароли, номера карт, персональные данные (например, `console.log(token)` в прокси недопустим).
- Ответы API не содержат лишних полей (`passwordHash`, внутренние флаги): используй `select` и response-DTO.
- Шифрование при передаче (HTTPS) и в покое там, где нужно (чувствительные поля, бэкапы).

## Зависимости и инфраструктура (A06, A08)

- `pnpm audit --prod`; новые зависимости проверяй на поддержку и необходимость; lock-файл коммитится.
- Docker: непривилегированный пользователь, закреплённые версии базовых образов, без секретов в слоях.
- GitHub Actions: минимальные `permissions`, закреплённые версии actions, осторожно с `pull_request_target` и подстановкой `${{ github.event.* }}` в `run`.

## Вебхуки и интеграции

- Подпись вебхука проверяется на сыром теле (Stripe и др.), обработка идемпотентна (см. `stripe-payments`).
- Исходящие запросы к сторонним API с таймаутами; ответы третьих сторон валидируются.

## Быстрый чек-лист перед сдачей

Guard и проверка владельца на каждом новом эндпоинте · DTO с whitelist · нет секретов и токенов в логах · нет `dangerouslySetInnerHTML` и raw SQL с вводом · `callbackUrl` / редиректы проверены · `pnpm audit` без high/critical.
