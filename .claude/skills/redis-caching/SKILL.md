# Redis и кэш (apps/api)

Приоритет у правил репозитория (`CLAUDE.md`). Код: `src/modules/redis` (клиент `REDIS_CLIENT`, ioredis), `src/modules/cache` (`CacheService`), метрики hit/miss в `src/modules/metrics`. Очереди BullMQ и RabbitMQ описаны в скилле `queues-bullmq-rabbitmq`.

## Правила

1. Кэш только через `CacheService` (`get<T>`, `set(key, value, ttl)`, `del`). Он отказоустойчивый: при падении Redis работает как промах. Не вызывай `redis` напрямую для кэша, не бросай ошибку из-за кэша.
2. Источник правды всегда БД. Кэш можно потерять в любой момент, приложение должно работать без него.
3. Ключи: `<домен>:<сущность>:<id>[:<вариант>]`, например `plans:list`, `user:<id>:billing`. Данные пользователя всегда с его id в ключе: общий ключ на персональные данные это утечка.
4. TTL задавай явно по смыслу данных. Для изменяемых данных инвалидируй `del` в той же операции, что меняет БД (после успешной записи).
5. Не кэшируй: секреты, токены, одноразовые коды, платёжные данные.
6. Кэшируй сериализуемое (JSON), не Prisma-объекты с `Date`/`BigInt` без преобразования: после `JSON.parse` даты станут строками.
7. Защита от шторма: для дорогих ключей с высоким трафиком не ставь одинаковый TTL на массу ключей сразу (добавь разброс) и не пересчитывай один ключ параллельно из многих запросов.
8. Rate limiting на auth, отправку SMS и email и дорогие эндпоинты (`@nestjs/throttler` или счётчик в Redis с `INCR` + `EXPIRE`), с лимитом на пользователя или IP.
9. Тесты: unit с моком `REDIS_CLIENT` (образец `cache.service.spec.ts`): попадание, промах, ошибка Redis, невалидный JSON.

## Проверка

`pnpm --filter api typecheck`, `lint`, `test`. Смотри метрики hit/miss после включения нового кэша: hit-rate около нуля значит неудачный ключ или слишком короткий TTL.
