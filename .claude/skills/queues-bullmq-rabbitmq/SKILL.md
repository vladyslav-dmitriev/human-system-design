# BullMQ и RabbitMQ

Приоритет у правил репозитория (`CLAUDE.md`). Образцы кода: `apps/api/src/modules/rabbitmq` (producers, consumers, bindings, serializers, health), BullMQ через `@nestjs/bullmq`, Redis через `ioredis`.

## Выбор

- **BullMQ**: отложенные и повторяющиеся задачи, ретраи, приоритеты, лимиты скорости, когда producer и worker это один сервис.
- **RabbitMQ**: события между сервисами, роутинг по топикам, fan-out, несколько независимых консьюмеров.
- Не дублируй: если для сценария уже есть очередь, используй её.

## Общие правила

1. **Идемпотентность обязательна.** Сообщение может прийти дважды. Используй уникальный ключ операции (id сообщения / бизнес-id) и проверку «уже обработано» (уникальный индекс в БД, `upsert`, таблица обработанных id), либо делай операцию естественно идемпотентной.
2. Полезная нагрузка маленькая и версионируемая: id и тип, а не вся сущность; читай актуальные данные из БД при обработке. Валидируй входящее сообщение (DTO / zod), не доверяй содержимому.
3. Ошибки: различай **временные** (сеть, таймаут → ретрай с backoff) и **постоянные** (невалидные данные → сразу в dead-letter, без бесконечных ретраев).
4. Не глотай ошибки: логируй с id задачи и причиной, без чувствительных данных (токены, пароли, персональные данные).
5. Секреты и строки подключения только из конфига (`src/config`) и env.
6. Побочные эффекты (письмо SendGrid, вызов Stripe, запись в S3) передавай идемпотентный ключ или проверяй состояние перед повтором.
7. Graceful shutdown: дай воркерам завершить текущие задачи (`worker.close()`, `app.enableShutdownHooks()`).

## BullMQ

- `attempts` + `backoff: { type: "exponential", delay }`; `removeOnComplete` / `removeOnFail` с лимитами, чтобы Redis не рос бесконечно.
- Свой `jobId` для дедупликации (повторная постановка с тем же id игнорируется).
- Долгие задачи: `job.updateProgress`, ограничение `concurrency`, не блокируй event loop CPU-тяжёлой работой (выноси в sandboxed processor).
- Зависшие задачи (`stalled`) и упавшие мониторь; обработчики `failed` / `error` обязательны.
- Redis: общий connection с `maxRetriesPerRequest: null` для воркеров BullMQ.

## RabbitMQ

- `durable` очереди и exchange, `persistent` сообщения для важных данных.
- Ручной `ack` после успешной обработки, `nack` / `reject` с `requeue: false` для постоянных ошибок.
- Dead-letter exchange и очередь для необрабатываемых сообщений; retry-очередь с TTL для отложенного повтора, ограничение числа попыток (заголовок счётчика), чтобы не зациклить.
- `prefetch` (QoS) задавай явно, чтобы один консьюмер не забирал всё.
- Переподключение к брокеру при разрыве; health-check (`rabbitmq.health.ts`) обновляй вместе с изменениями топологии.
- Топологию (exchange, queue, binding) объявляй в одном месте (`bindings`), а не в разных консьюмерах.

## Тесты

- Unit: обработчик как чистая функция с замоканными зависимостями; проверь повторную доставку (второй вызов не создаёт дубля).
- Не используй реальный брокер и боевые очереди в тестах.
