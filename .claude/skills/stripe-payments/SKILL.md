# Stripe

Приоритет у правил репозитория (`CLAUDE.md`). Код оплат: `apps/api/src/modules/billing` (`payments`, `subscription`, `invoice`, `payment-method`, `product`); web: `@stripe/stripe-js`, `@stripe/react-stripe-js`. Сверяйся с актуальной документацией Stripe (SDK `stripe` 22.x), не пиши по памяти.

## Жёсткие правила

1. **Только тестовый режим** при разработке и тестах: ключи `sk_test_…` / `pk_test_…`. Никогда не используй и не вставляй live-ключи; выполнять реальные платежи, возвраты и списания нельзя без явного подтверждения пользователя.
2. Секретный ключ и webhook secret только на сервере (env, `src/config`), не в `NEXT_PUBLIC_*`, не в логах, не в образах. На клиент идёт только publishable key.
3. **Сумма, валюта и цена определяются на сервере** (по id продукта / цены из БД или Stripe), а не приходят из тела запроса клиента.
4. Данные карт никогда не касаются вашего сервера: только Stripe Elements / Checkout. Не логируй и не храни PAN, CVC.

## Вебхуки

- Проверяй подпись: `stripe.webhooks.constructEvent(rawBody, signature, secret)`. Нужно **сырое тело** (в Nest: `rawBody: true` при создании приложения или отдельный raw-парсер для маршрута вебхука), а не распарсенный JSON.
- Обработка **идемпотентна**: событие может прийти повторно и не по порядку. Сохраняй `event.id`, пропускай уже обработанные; не полагайся на порядок событий, перечитывай актуальный объект из Stripe при необходимости.
- Отвечай `2xx` быстро; тяжёлую работу вынеси в очередь (скилл `queues-bullmq-rabbitmq`).
- Источник правды о статусе платежа и подписки: вебхуки (а не редирект пользователя на success-страницу).
- Эндпоинт вебхука без JWT-guard, но с проверкой подписи; никакие другие публичные эндпоинты не создавай ради этого.

## Платежи и подписки

- Мутации Stripe с `idempotencyKey` (например, id заказа или операции), чтобы повторный запрос не создал второй платёж.
- Привязывай `stripeCustomerId` к пользователю; перед операциями проверяй, что ресурс (подписка, счёт, способ оплаты) принадлежит текущему пользователю (защита от IDOR).
- Состояния: используй статусы Stripe (`requires_action`, `processing`, `succeeded`, `past_due`, `canceled`) и обрабатывай все, включая 3-D Secure и неудачные продления.
- Ошибки Stripe (`StripeCardError`, `StripeInvalidRequestError`, …) переводи в понятные HTTP-ошибки; пользователю не показывай сырой текст и внутренние id.
- Деньги: целые минимальные единицы (центы), не `float`.

## Фронтенд

- `loadStripe` один раз (вне компонента); `Elements` с `clientSecret`, который получен от вашего API.
- После оплаты не считай успех по редиректу: покажи «обрабатывается» и дождись статуса от API.
- Тексты ошибок и подписи через next-intl; сообщения Stripe (`error.message`) локализуются на стороне Stripe через `locale`.
- Состояния загрузки и ошибки у кнопок оплаты, защита от двойного клика.

## Тестирование

- Тестовые карты Stripe: `4242 4242 4242 4242` (успех), `4000 0025 0000 3155` (3-D Secure), `4000 0000 0000 9995` (отказ). Любая будущая дата и CVC.
- Вебхуки локально: `stripe listen --forward-to localhost:<port>/<webhook-path>` и `stripe trigger <event>`; для unit-тестов собирай событие с подписью через `stripe.webhooks.generateTestHeaderString`.
- В e2e мокай Stripe или используй тестовый режим, но не реальные аккаунты и карты.
