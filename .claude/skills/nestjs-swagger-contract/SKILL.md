# Контракт web ↔ api

Приоритет у правил репозитория (`CLAUDE.md`): меняете контракт, обновляйте обе стороны и `apps/web/api.ts` в одном изменении, либо явно опишите, что осталось другой стороне.

Swagger подключается в `apps/api/src/setup-swagger.ts`. Типов клиента из OpenAPI сейчас нет: URL лежат в `apps/web/api.ts`, типы ответов пишутся вручную.

## Как менять эндпоинт

1. Опиши контракт до кода: метод, путь, query/body, ответ, коды ошибок, кто имеет доступ.
2. API: DTO запроса и ответа классами с `@ApiProperty`, на методе `@ApiOperation` и `@Api*Response` для каждого кода (200/201, 400, 401, 403, 404, 409). Ответ через Response DTO, не прямой Prisma-объект (не утекут лишние поля).
3. Web: добавь функцию URL в `apps/web/api.ts` в нужную группу (`NEXT_PUBLIC_API_CLIENT_URL` для браузера, `NEXT_PUBLIC_API_SERVER_URL` для серверных компонентов) и тип ответа рядом с использованием.
4. Обратная совместимость: добавление необязательных полей безопасно; переименование, удаление поля и смена типа ломают клиент. Ломающее изменение делай в два шага (сначала API поддерживает оба варианта, потом web, потом удаление старого) и опиши в отчёте.
5. Проверь по живому Swagger (путь смотри в `setup-swagger.ts`), что схема отражает реальный ответ.

## Типы на клиенте

Разовое улучшение: генерация типов из OpenAPI (например `openapi-typescript`) в `packages/` или `apps/web/shared/types`, чтобы расхождения ловил `typecheck`. До этого типы ответов сверяй с Response DTO вручную, и `reviewer` должен это проверять.

## Чек-лист ревью

- Каждый новый эндпоинт имеет Swagger-описание и guard.
- Есть запись в `apps/web/api.ts` или явная пометка, что фронт не обновлён.
- Коды ошибок обработаны на фронте (форма показывает 400/409, 401 ведёт на логин).
- В ответе нет секретов, хешей паролей, внутренних id, которые клиенту не нужны.
